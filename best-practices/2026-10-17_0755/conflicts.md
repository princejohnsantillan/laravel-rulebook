### 2. readonly: Immutable property policy: avoid readonly keywords by default versus require readonly for never-reassigned dependencies and values
- **Decision (2026-10-18, by the user):** Keep style-032 (readonly promoted constructor properties by default) as the rule. Reword http-180 into its exception: skip readonly on properties that the framework or a package fills in or changes after construction (form objects, Livewire/Filament form state, Eloquent models).
- Side A: **Apply readonly only for deliberate immutability** (`http-180`), score 4 (community 1, linters 2)
  - Do: Do not add readonly to properties or classes by default; let the context (DTO, resource) signal read-only intent instead of the extra keyword.
  - Spatie PHP guidelines - class defaults ('readonly: we haven't come across any problems that readonly would solve'; don't use final or readonly by default) - https://spatie.be/guidelines/php#content-class-defaults
- Side B: **Use readonly promoted properties for immutable data** (`style-032`), score 9 (teaching/blog 1, packages 2, first-party 3, laracon 3)
  - Do: Use readonly promoted properties for dependencies or value fields that should not be reassigned, and expose simple DTO data directly when getters add no behavior.
  - Laravel 13.x docs: Images - custom transformations (public readonly int $size) - https://laravel.com/docs/13.x/images#custom-transformations
  - Laracon Online Winter 2022 - Ryuta Hamasaki (DTOs with promoted readonly properties) - https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=5380s
  - spatie/laravel-data DataCollection (public readonly promoted property) - https://github.com/spatie/laravel-data/blob/ce296f22861dc1237ce468754cc7f46d3ac34ad5/src/DataCollection.php#L60
  - filamentphp/filament WidgetConfiguration (public readonly promoted property) - https://github.com/filamentphp/filament/blob/7e268d74423d641d0935bac223246c889456487e/packages/widgets/src/WidgetConfiguration.php#L12
  - ashallendesign.co.uk - 20 useful Laravel tips (readonly DTOs without getters) - https://ashallendesign.co.uk/blog/20-useful-laravel-tips
- Claude's assessment before the decision: These give opposite defaults for the same code: for a never-reassigned injected dependency or a DTO field, style-032 says add readonly, while http-180 (Spatie) says leave it off, even on DTOs, unless immutability is a deliberate requirement. style-032 has broader sources (packages, Laracon 2022, the L13 Images docs' Pixelate transformation with public readonly) but aspirational adoption (about 6% of sampled code; laravel/framework mostly promotes dependencies without readonly), whereas http-180 matches what code actually does. Neither is outdated for L13 (PHP >= 8.3); a reasonable middle ground is readonly for value objects and DTOs, optional for injected services.
- Now `http-180` (Should): **Skip readonly on properties the framework or a package hydrates or mutates after construction**. Exception to style-032: leave properties writable (no readonly) on classes whose state the framework or a package fills in or changes after construction, such as Livewire form objects and component properties, Filament form state, Eloquent models and other hydrated objects.
- Now `style-032` (Must, aspirational): **Make promoted constructor properties readonly by default**. By default, declare promoted constructor properties readonly for dependencies and value fields that are not reassigned after construction, and expose simple DTO data directly when getters add no behavior. Exception: skip readonly where the framework or a package fills in or changes the property after construction (see http-180).

### 3. Test data: Mutable fixture setup policy: create records explicitly inside each test versus create shared fresh fixtures in beforeEach
- **Decision (2026-10-18, by the user):** Merge testing-183 into testing-092: create the records each test needs with factories inside the test by default; use beforeEach only for setup every test in the file shares (e.g. an authenticated user).
- Side A: **Keep mutable fixture creation visible in each test** (`testing-092`), score 10 (boost 3, teaching/blog 1, laracon 3)
  - Do: Create mutable records inside the test or an explicitly called helper; reserve shared setup hooks for configuration.
  - laravel/boost skill testing-best-practices/test-data (do not create records in beforeEach/setUp) - https://github.com/laravel/boost/blob/f1411f90d54cb01ffe30606b7ca92789aad737d9/.ai/laravel/skill/testing-best-practices/rules/test-data.blade.php#L10
  - laravel/boost skill testing-best-practices/review (beforeEach holds configuration only) - https://github.com/laravel/boost/blob/f1411f90d54cb01ffe30606b7ca92789aad737d9/.ai/laravel/skill/testing-best-practices/rules/review.blade.php#L42
  - Laracon EU 2024 - Managing 5000+ Tests Efficiently - https://www.youtube.com/watch?v=tDqPe8LbWEI&t=848s
  - Mastering Laravel - Why we like minimal seeders for tests - https://masteringlaravel.io/daily/2023-12-05-why-we-like-minimal-seeders-for-tests
- Side B: **Recreate shared fixtures before each case** (`testing-183`), score 9 (community 1, packages 2, first-party 3)
  - Do: Use beforeEach() to create fresh shared fixtures and expose them on the test instance.
  - laravel/fortify ConfirmablePasswordControllerTest (creates user in afterRefreshingDatabase hook) - https://github.com/laravel/fortify/blob/7aa4ac434062c2f4754985ab74adb1dcb11f1123/tests/ConfirmablePasswordControllerTest.php#L20
  - Stack Overflow - Pest beforeEach shares state via $this - https://stackoverflow.com/a/74288606
  - pestphp/pest tests/Features/BeforeEach.php (hook mechanics, scalar state) - https://github.com/pestphp/pest/blob/e9fa0f50c5c6f11be77bf8d69ba121c9f0b54d8c/tests/Features/BeforeEach.php#L3
- Claude's assessment before the decision: Genuine conflict: testing-183 prescribes exactly what testing-092 forbids, beforeEach(fn () => $this->user = User::factory()->create()), so the two cannot both hold for database records. testing-092 has explicit first-party L13 guidance behind it (Boost testing skill: do not create records in beforeEach() or setUp()) plus Laracon EU 2024, while testing-183 rests on a 2022 Stack Overflow answer, Pest's own test of the hook mechanism (scalar state, not records), and one Fortify package test that seeds a user in afterRefreshingDatabase. Neither is mechanically outdated (beforeEach and $this binding still work in Pest 3/4), but testing-092 should be the default, with testing-183 narrowed to fresh non-record fixtures such as fakes, doubles and payloads.
- Now `testing-092` (Should): **Create each test's records inside the test; use beforeEach only for setup every test shares**. By default, create the records a test needs with factories inside that test, or in a helper the test calls explicitly. Use beforeEach() (or setUp()) only for setup that every test in the file needs, such as an authenticated user, fakes or configuration, so each test still gets fresh state.
- Now `testing-183`: merged into testing-092

## Checked and found compatible (11)
- `config-143` Import class and facade symbols explicitly instead of relying on global aliases or repeated fully qualified references / `style-124` Fully qualify globals under the Symfony policy: Mostly compatible: config-143 targets namespaced Laravel classes reached through global facade aliases (\Cache -> use Illuminate\Support\Facades\Cache), and importing those also satisfies the Symfony fully-qualify-globals policy. The rules overlap only on true root-namespace symbols (\DateTimeImmutable, \strlen), where config-143's flag_when defers to the project's import policy and style-124 applies only to @Symfony-preset projects. Neither is outdated: L13 still registers Facade::defaultAliases(), so \Cache resolves, but explicit imports are the tooling-backed form, and Pint's default laravel preset leaves global_namespace_import unconfigured.
- `http-292` Write string concatenations without spaces around the dot operator / `style-142` Space concatenation operators under the custom policy: These are mutually exclusive settings of the same concat_space fixer, but scope-dependent: http-292 is the default of Pint's laravel preset and first-party code, while style-142 applies only when a project deliberately overrides it (Filament's pint.json, Pint's per/symfony presets), and Pint enforces whichever is configured. Neither is outdated, and the no-space form is the L13 default. http-292 should say it applies under the default laravel preset so it doesn't flag projects that chose PER spacing.
- `infra-007` Automatically fix and commit formatting in CI / `testing-221` Check formatting without mutating code in validation jobs: Compatible, because the rules cover different jobs: infra-007 is an opt-in fixer workflow that rewrites and commits formatting on push (the L13 Pint docs' own GitHub Actions example; the shared laravel/.github workflow in Pulse and Pennant), while testing-221 keeps test and validation scripts read-only with pint --test (L13 Pint docs; starter-kit composer test scripts). A repository can do both; the real choice is only whether CI repairs drift or just blocks it, and a check job on the same push should run after the fixer or tolerate its commit. Both are current for L13.
- `style-006` Prefer PascalCase enum cases / `style-008` Use uppercase enum cases under that convention: Both are conditional on the project's chosen enum convention (style-006 when no conflicting style exists, style-008 only after adopting the uppercase guide), so they are alternatives, not simultaneous obligations. PascalCase is the L13-aligned default (Boost, Spatie, the L13 routing docs' enum example). The uppercase side rests on one 2022 personal style guide: not technically outdated, but out of step with current Laravel convention, so it fits only legacy codebases that already use it.
- `style-124` Fully qualify globals under the Symfony policy / `style-139` Import classes and globals under the import policy: These are opposite settings of the same global_namespace_import fixer, but each rule is gated on the project's declared policy, so a project follows exactly one. Pint's default laravel preset leaves this unconfigured; first-party laravel/boost and laravel/package-skeleton opt into importing (style-139), while fully qualifying (style-124) comes only from the @Symfony ruleset. That makes style-139 the Laravel-aligned choice and style-124 an opt-in for Symfony-preset projects; neither is outdated for L13.
- `testing-092` Keep mutable fixture creation visible in each test / `testing-109` Extract repeated setup into scoped hooks: Compatible as worded, and Boost states both: hooks for configuration repeated in every test, mutable records created in the test or in a helper it calls explicitly; testing-109's first-party evidence is all configuration or explicit helpers (Pulse setTestNow, Reverb container doubles, Laracasts loginAsUser), not record creation. The only clash is testing-109's example_after, which creates a User in beforeEach and so contradicts testing-092; rewrite it (hook for actingAs or fakes, helper for records). Both are L13-current.
- `testing-134` Prefer Pest for new suites / `testing-203` Prefer PHPUnit and Mockery for class-based unit suites: Scope-dependent: testing-134 makes Pest the default only when no PHPUnit convention exists, and testing-203 applies only once a project has chosen PHPUnit, so a project follows one. The L13 testing docs treat both as first-class (Pest/PHPUnit tabs); laravel/laravel and the starter kits ship class-based PHPUnit tests with Pest offered as an installer option, while newer first-party packages (Pulse, Reverb, package-skeleton) and the Livewire docs use or recommend Pest. The 2022 alexeymezenin table that lists Pest as not recommended is outdated, but class-based PHPUnit itself is fully current.
- `validation-002` Keep small single-use validation inline / `validation-003` Use a Form Request for each meaningful input action: Mostly compatible, with a threshold that Boost and the L13 docs both state: use a Form Request when validation or authorization is substantial, reused, or clearer outside the controller, and inline $request->validate() for a small endpoint-specific set, so both rules hold if validation-003's 'meaningful input' means non-trivial. They collide only on tiny single-use rulesets under validation-003's stricter per-action convention, which blogs, Shift and the starter kits follow (they use Form Requests even for small settings forms). Neither is outdated; reword validation-003 with Boost's threshold.
- `validation-003` Use a Form Request for each meaningful input action / `validation-214` Inject request-backed Data objects at controller boundaries: These are alternative validation boundaries: validation-214 applies only when a project has adopted spatie/laravel-data as its request boundary (Data classes validate input, run authorize(), and map it before the action), in which case a parallel Form Request would duplicate the rules; otherwise validation-003 governs. Neither is outdated: laravel-data supports illuminate ^13.0, and Form Requests are Laravel's built-in default. Scope validation-003 with 'unless the project uses request-backed Data objects'.
- `http-076` Read request input with $request->name or request('name') instead of the verbose $request->input()/Request::get() forms / `http-380` Use the injected request object in controllers and middleware instead of equivalent request facade or helper calls: Compatible and scope-dependent: http-076 allows $request->name or request('name'), so controllers and middleware that inject Request can use $request->name and satisfy both, while request('name') stays fine where nothing is injected (TLint only rewrites request()->get('k') to request('k') and does not prefer the helper over an injected instance). The only direct clash is http-076's example_after, request('name'), which is exactly http-380's example_before. http-076 is partly outdated for L13: framework 13.37 deprecates Request::get() with the note 'use ->input() instead', so input() is the canonical form, not a verbose one to avoid; reword http-076 to target ->get() and to prefer the injected $request when one exists.
- `http-180` Apply readonly only for deliberate immutability / `style-033` Declare wholly immutable DTOs readonly: Mostly compatible, because they answer different questions: http-180 decides whether to use readonly at all (only for deliberate immutability, e.g. the value objects in Nuno Maduro's toBeReadonly() arch tests), and style-033's flag_when only fires once every DTO property is already readonly, when it says to make the class readonly instead. The remaining clash is wording: http-180's do-text names DTOs as needing no keyword, while style-033's 'immutable' could be read semantically, so reword it to 'already deliberately readonly'. Neither side is outdated for L13 (PHP >=8.3 has readonly classes; the Spatie guideline is from 2026, and first-party framework and Boost skip automatic readonly); the 2022 blog sources explain the PHP 8.2 feature rather than set Laravel policy.
