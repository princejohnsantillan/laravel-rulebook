# Laravel Codebase Rules

**Version:** 2026-10-13 18:19 (Asia/Manila)

**Scope:** Application code for Laravel 13 and current first-party tools: architecture, routing, Eloquent, security, performance, testing, frontend stacks, and package building.

**Levels:** **Must** = score 7+ · **Should** = score 4–6 · **Consider** = score 2–3. Score = sum of points from independent sources (official 3, tier 1 3, Laracon speaker 2 or 3 for employees, tier 2 2–3, tier 3 1).

**Sub-bullets:** *Why* = the reason behind the rule, quotable when flagging a violation · *Flag when* = an observable signal in a diff that suggests a violation (omitted when not observable in code).

*Written for code-reviewing agents: use these rules to evaluate diffs, not as an implementation checklist.*

*Each rule lists its score and every independent source (tier, points).*

**Known limitations of this version:**
- Tier 2 was built from the following lists of tier 1 accounts, and X truncated those lists, so some accounts followed by 5+ employees may be missing from tier 2.
- Paid Laracasts episodes were covered from their public descriptions and lesson notes only, not full transcripts.
- Rules extracted from blogs (Securing Laravel, aaronfrancis.com, Spatie, Tighten, freek.dev and others) are machine summaries of each article, not direct quotes; follow the link before quoting.
- Official sources (Laravel docs, Boost, first-party code, Pint/Larastan, product docs) count as one org; Spatie and Freek count as one org; each person counts once per rule at the highest tier among their evidence for that rule.

## General

### Architecture & structure

- **Must** Start simple, tolerate duplication until a stable shared responsibility emerges, and add abstractions only when they clearly pay off. — score 30: [Christoph Rumpel](https://www.youtube.com/watch?v=f4QShF42c6E&t=24315s) (Laracon speaker (employee), 3); [Josh Cirre](https://laracasts.com/episodes/3325) (Tier 1, 3); [Laravel (official)](https://laravel.com/docs/13.x/structure) (Official, 3); [Nuno Maduro](https://x.com/enunomaduro/status/1786742287885545696) (Tier 1, 3); [Jo Minney](https://www.youtube.com/watch?v=seX4HqMIAMk) (Laracon speaker, 2); [Luke Downing](https://www.youtube.com/watch?v=GERCwd65O-8) (Laracon speaker, 2); [Mary Perry](https://www.youtube.com/watch?v=vsxoaTgtyjw) (Laracon speaker, 2); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk) (Laracon speaker, 2); [Ryan Lovett](https://www.youtube.com/watch?v=AJ8MOFoDeP0) (Laracon speaker, 2); [Spatie](https://spatie.be/docs/laravel-multitenancy/v4/introduction) (Tier 2, 2); [Tighten](https://tighten.com/insights/are-your-queue-workers-working) (Tier 2, 2); [@GioDev8](https://x.com/GioDev8/status/1535423272531132416) (Tier 3, 1); [Jason McCreary](https://laracasts.com/episodes/3643) (Tier 3, 1); [Jeffrey Way](https://laracasts.com/episodes/3883) (Tier 3, 1); [Katerina Trajchevska](https://laracasts.com/episodes/3160) (Tier 3, 1)
  - Why: avoids coupling merely similar business rules through premature abstractions.
  - Flag when: A shared abstraction gains feature-specific switches to accommodate unrelated business rules.
- **Must** Inject typed dependencies and let the container autowire them; add bindings only where the implementation or construction must be chosen. — score 28: [Christoph Rumpel](https://christoph-rumpel.com/2024/9/all-laravel-php-attributes-at-your-disposal) (Tier 1, 3); [Joe Tannenbaum](https://blog.joe.codes/starting-a-toggl-timer-from-the-command-line-with-laravel-zero) (Tier 1, 3); [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3); [Mohamed Said](https://laracasts.com/episodes/2777) (Tier 1, 3); [Luke Downing](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=1500s) (Laracon speaker, 2); [Mary Perry](https://www.youtube.com/watch?v=KroiagwnV0s) (Laracon speaker, 2); [Steve McDougall](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=22075s) (Laracon speaker, 2); [laravel/framework PR author cosmastech](https://github.com/laravel/framework/pull/56383) (Tier 2, 2); [laravel/framework PR author riasvdv](https://github.com/laravel/framework/pull/56334) (Tier 2, 2); [laravel/framework PR author yitzwillroth](https://github.com/laravel/framework/pull/55904) (Tier 2, 2); [Dan Harrin](https://x.com/danjharrin/status/1501598779056734213) (Tier 3, 1); [Jeffrey Way](https://laracasts.com/episodes/3436) (Tier 3, 1); [Jeremy McPeak](https://laracasts.com/episodes/4132) (Tier 3, 1); [Katerina Trajchevska](https://laracasts.com/episodes/3144) (Tier 3, 1)
  - Why: makes collaborators explicit and substitutable in tests without requiring manual construction everywhere.
  - Flag when: A service constructs a replaceable collaborator internally instead of accepting a typed dependency.
- **Must** Draw boundaries around business contexts, exposing small public interfaces named in domain language and hiding internals. — score 20: [Ashley Hindle](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=31692s) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/container) (Official, 3); [Wendell Adriel](https://wendelladriel.com/blog/modular-monoliths-creating-real-boundaries-before-reaching-for-microservices) (Tier 1, 3); [Bobby Bouwmann](https://www.youtube.com/watch?v=jX3nWXyLank) (Laracon speaker, 2); [Mary Perry](https://www.youtube.com/watch?v=vsxoaTgtyjw) (Laracon speaker, 2); [Mateus](https://www.youtube.com/watch?v=WqL6wgH1fKs) (Laracon speaker, 2); [Ryuta Hamasaki](https://www.youtube.com/watch?v=X6xPG6DJibg) (Laracon speaker, 2); [Spatie](https://www.youtube.com/watch?v=CrO_7Df1cBc) (Laracon speaker, 2); [Mateus Guimarães](https://laracasts.com/episodes/3034) (Tier 3, 1)
  - Why: keeps business terms unambiguous within contexts and isolates changes behind explicit interfaces.
  - Flag when: Code in one business context directly accesses another context’s internal implementation.
- **Must** Extract reusable or growing business operations into focused actions with explicit inputs and useful return values; compose them for larger workflows. — score 16: [Laravel (official)](https://github.com/laravel/react-starter-kit/tree/main/app/Actions) (Official, 3); [Nuno Maduro](https://github.com/nunomaduro/essentials) (Tier 1, 3); [Luke Downing](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=1500s) (Laracon speaker, 2); [Mary Perry](https://www.youtube.com/watch?v=vsxoaTgtyjw) (Laracon speaker, 2); [Mateus](https://www.youtube.com/watch?v=WqL6wgH1fKs) (Laracon speaker, 2); [Jeffrey Way](https://laracasts.com/episodes/3906) (Tier 3, 1); [Jeremy McPeak](https://laracasts.com/episodes/4128) (Tier 3, 1); [Mateus Guimarães](https://laracasts.com/episodes/3036) (Tier 3, 1); [Simon Vrachliotis](https://laracasts.com/episodes/3667) (Tier 3, 1)
  - Why: keeps entry points thin and makes operations independently reusable and testable.
  - Flag when: Controllers, commands, or jobs duplicate a business operation or call another entry point to reuse its behavior.
- **Must** Use Laravel and established packages where they fit; write custom code only when business needs justify maintaining it. — score 16: [Joe Dixon](https://laracasts.com/episodes/3402) (Tier 1, 3); [Laravel (official)](https://laravel.com/docs/13.x/installation) (Official, 3); [Mary Perry](https://www.youtube.com/watch?v=w7jKcbVcI54) (Laracon speaker, 2); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk) (Laracon speaker, 2); [Ruchit Patel](https://www.youtube.com/watch?v=MdIli5VczSU) (Laracon speaker, 2); [Spatie](https://spatie.be/blog/the-robots-are-replacing-the-packages) (Tier 2, 2); [Tighten](https://tighten.com/insights/bol-ep13-gilbert-pellegrom-lemon-squeezy) (Tier 2, 2)
  - Why: frees development time for business features and reduces custom code maintenance.
  - Flag when: New custom infrastructure duplicates suitable Laravel facilities or an established package already in use.
- **Must** Define feature-specific fallbacks for external dependency failures, keep unrelated features usable, and disclose stale or unavailable data. — score 15: [Laravel (official)](https://laravel.com/docs/13.x/cache) (Official, 3); [Taylor Otwell](https://x.com/taylorotwell/status/1932810338262765569) (Tier 1, 3); [Harris Raftopoulos](https://www.youtube.com/watch?v=E9t2lVn0z8A) (Laracon speaker, 2); [Ryan Lovett](https://www.youtube.com/watch?v=AJ8MOFoDeP0) (Laracon speaker, 2); [Spatie](https://freek.dev/3194-detecting-spam-and-auto-replies-with-jev-and-the-laravel-ai-sdk) (Tier 2, 2); [Zuzana Kunckova](https://www.youtube.com/watch?v=MUlln-pnk3U) (Laracon speaker, 2); [Sabatino Masala](https://x.com/SabatinoMasala/status/1784182024032411950) (Tier 3, 1)
  - Why: limits dependency outages to the capabilities that actually require them.
  - Flag when: An external service failure breaks unrelated features or silently presents cached data as current.
- **Must** Keep reusable business logic independent of HTTP and UI concerns; accept plain inputs and leave transport-specific responses in entry points. — score 13: [Aaron Francis](https://www.youtube.com/watch?v=lXjYStxGFIQ) (Laracon speaker (employee), 3); [Nuno Maduro](https://github.com/pestphp/pest/blob/5.x/src/ArchPresets/Laravel.php) (Tier 1, 3); [Duilio Palacios](https://www.youtube.com/watch?v=1sixoOQliZI) (Laracon speaker, 2); [Luke Downing](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=1500s) (Laracon speaker, 2); [Paul Dragoonis](https://x.com/dr4goonis/status/1647246295914930176) (Tier 2, 2); [Stephen Rees-Carter](https://securinglaravel.com/in-depth-a-deep-dive-into-laravels-new-starter-kits-pt-2) (Tier 3, 1)
  - Why: allows the same operation to run and be tested through HTTP, CLI, or other interfaces.
  - Flag when: A reusable service or action accepts an HTTP Request, renders views, redirects, or manages session login.
- **Must** Start from an official starter kit, then delete what the product doesn't need. — score 13: [Josh Cirre](https://www.youtube.com/watch?v=RY6wrHaLeCo) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/starter-kits) (Official, 3); [Taylor Otwell](https://x.com/taylorotwell/status/1862911447375786451) (Tier 1, 3); [Matt Stauffer](https://speakerdeck.com/mattstauffer/what-to-do-after-laravel-new) (Laracon speaker, 2); [Will King](https://www.youtube.com/watch?v=LN3heGluQ7A&t=840s) (Laracon speaker, 2)
  - Why: provides established application conventions and scaffolding matched to required features.
- **Must** Use facades where their concise API clarifies service access and preserves testability, keeping hidden dependencies out of core business logic. — score 12: [Christoph Rumpel](https://www.youtube.com/watch?v=f4QShF42c6E&t=24315s) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/facades) (Official, 3); [Jason McCreary](https://www.youtube.com/watch?v=LaKEFjA25r4) (Laracon speaker, 2); [Luke Downing](https://www.youtube.com/watch?v=GERCwd65O-8) (Laracon speaker, 2); [Mary Perry](https://www.youtube.com/watch?v=w7jKcbVcI54) (Laracon speaker, 2)
  - Why: allows idiomatic framework service access without obscuring important business collaborators.
  - Flag when: A facade-based call hides a central business dependency or bypasses available service fakes.
- **Must** Encapsulate external API access in a dedicated client with centralized request settings and typed boundary data where it clarifies the contract. — score 11: [Laravel (official)](https://laravel.com/docs/13.x/container) (Official, 3); [Kévin Dunglas](https://www.youtube.com/watch?v=DJJt_2V26V8) (Laracon speaker, 2); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk) (Laracon speaker, 2); [Spatie](https://spatie.be/blog/utilizing-claude-skills-in-client-projects) (Tier 2, 2); [Steve McDougall](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=22075s) (Laracon speaker, 2)
  - Why: isolates provider details and makes integrations easier to replace or fake.
  - Flag when: Business callers repeat provider URLs, timeouts, parameter construction, or untyped response mapping.
- **Must** Split classes with too many responsibilities into objects for each distinct domain concept. — score 10: [James Brooks](https://x.com/jbrooksuk/status/1928824002144768458) (Tier 1, 3); [Laravel (official)](https://laravel.com/docs/13.x/structure) (Official, 3); [Duilio Palacios](https://www.youtube.com/watch?v=1sixoOQliZI) (Laracon speaker, 2); [Jeffrey Way](https://laracasts.com/episodes/3435) (Tier 3, 1); [Katerina Trajchevska](https://laracasts.com/episodes/3140) (Tier 3, 1)
  - Why: makes behavior easier to describe and test with less extensive mocking.
  - Flag when: A class gains behavior for distinct domain concepts alongside its existing unrelated responsibilities.
- **Must** Use guard clauses and early returns to keep the main path flat and readable. — score 10: [Laravel (official)](https://laravel.com/docs/13.x/collections) (Official, 3); [Duilio Palacios](https://www.youtube.com/watch?v=1sixoOQliZI) (Laracon speaker, 2); [Jason McCreary](https://www.youtube.com/watch?v=sBpzYsMgLK8) (Laracon speaker, 2); [Spatie](https://spatie.be/blog/spatie-guidelines-as-ai-skills) (Tier 2, 2); [Mateus Guimarães](https://laracasts.com/episodes/3590) (Tier 3, 1)
  - Why: keeps the primary operation visible at the outer indentation level.
  - Flag when: Failed prerequisite checks wrap the main operation in successive nested conditionals.
- **Must** Choose polling or broadcasting according to required freshness and operating cost; persist durable updates before broadcasting them. — score 8: [Joe Dixon](https://laracasts.com/episodes/3403) (Tier 1, 3); [Joe Tannenbaum](https://www.youtube.com/watch?v=v7spVsbN_Qc) (Laracon speaker (employee), 3); [Bert De Swaef](https://www.youtube.com/watch?v=xxAv6s5045Y) (Laracon speaker, 2)
  - Why: matches interface update complexity to user needs and keeps durable state authoritative.
  - Flag when: A feature introduces continuous realtime infrastructure without a freshness need or broadcasts durable changes before persistence.
- **Must** Refactor touched code in small, verified steps, proportionate to the change at hand. — score 8: [Laravel (official)](https://laravel.com/docs/13.x/testing) (Official, 3); [John Drexler](https://www.youtube.com/watch?v=YJmuKPk3d9M&t=11255s) (Laracon speaker, 2); [Jordan Havard](https://www.youtube.com/watch?v=riJBa0Bxo-8) (Laracon speaker, 2); [Katerina Trajchevska](https://laracasts.com/episodes/3220) (Tier 3, 1)
  - Why: makes the next feature easier to implement while preserving existing behavior.
- **Must** Start with one deployable app; extract services only when concrete benefits outweigh coordination and ops costs. — score 8: [Aaron Francis](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=11684s) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk) (Laracon speaker, 2)
  - Why: avoids extra operational and development overhead before measured constraints justify service extraction.
- **Must** Use execution-scoped context or container-managed state for shared contextual data instead of mutable statics or unnecessary argument threading. — score 8: [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3); [Tim MacDonald](https://x.com/timacdonald87/status/1549943424450580480) (Tier 1, 3); [Spatie](https://freek.dev/3203-laravel-context-the-hidden-information-that-follows-your-code) (Tier 2, 2)
  - Why: keeps contextual state testable and prevents leakage between long-lived execution lifecycles.
  - Flag when: A static property stores request-specific data or a singleton retains context across requests or jobs.
- **Must** In streamlined Laravel applications, configure routing, middleware, and exceptions in bootstrap/app.php, providers in bootstrap/providers.php, and schedules in routes/console.php or withSchedule(). — score 7: [Julien Bourdeau](https://x.com/julienbourdeau/status/1765424916013166929) (Tier 1, 3); [Laravel (official)](https://github.com/laravel/react-starter-kit/blob/717b8f55aefd82d25d4119eaebdc8e3a72b8d7e5/bootstrap/providers.php#L3-L8) (Official, 3); [Luke Downing](https://laracasts.com/episodes/3106) (Tier 3, 1)
  - Why: keeps framework configuration in the entry points used by the current application skeleton.
  - Flag when: A streamlined application adds Kernel classes or a config/app.php providers array to register framework configuration.
- **Should** Keep Laravel, PHP, and dependencies on supported versions and apply security fixes promptly. — score 6: [Laravel (official)](https://laravel.com/docs/13.x/releases) (Official, 3); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk&t=1680s) (Laracon speaker, 2); [Luke Downing](https://laracasts.com/episodes/3185) (Tier 3, 1)
  - Why: reduces exposure to vulnerabilities in unsupported or unpatched software.
  - Flag when: Dependency constraints or runtime images pin unsupported versions or releases with known security fixes.
- **Should** Modernize legacy code in small reviewed batches using Pint, static analysis, and Rector. — score 6: [Laravel (official)](https://laravel.com/docs/13.x/pint) (Official, 3); [Nuno Maduro](https://www.youtube.com/watch?v=328A3aFOy6M&t=660s) (Laracon speaker (employee), 3)
  - Why: reduces manual cleanup and exposes defects while progressively improving frequently changed legacy code.
- **Should** Register framework extensions and macros in service providers instead of editing vendor code or introducing unnecessary subclasses. — score 6: [Laravel (official)](https://laravel.com/docs/13.x/authentication#adding-custom-guards) (Official, 3); [Mohamed Said](https://laracasts.com/episodes/2780) (Tier 1, 3)
  - Why: centralizes extension setup and preserves dependency upgrades.
  - Flag when: A framework extension is installed ad hoc in business code or implemented by modifying vendor files.
- **Should** Use event sourcing selectively when durable domain history, auditability, or reconstruction is required; retain the events needed to derive state. — score 6: [Daniel Coulbourne](https://www.youtube.com/watch?v=tX6nBpSvh4s) (Laracon speaker, 2); [Josh Hanley](https://www.youtube.com/watch?v=evEU7ZAROlU) (Laracon speaker, 2); [Matt Stauffer](https://www.youtube.com/watch?v=f4QShF42c6E&t=13999s) (Laracon speaker, 2)
  - Why: preserves business changes and their context where current rows alone are insufficient.
  - Flag when: A workflow requiring historical reconstruction overwrites state without retaining the meaningful domain changes.
- **Should** Consolidate numerous simple container mappings in a dedicated provider’s bindings and singletons properties. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/providers#the-bindings-and-singletons-properties) (Official, 3); [Luke Downing](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=1500s) (Laracon speaker, 2)
  - Why: keeps implementation selection easy to inspect without repetitive registration code.
  - Flag when: A provider accumulates many equivalent bind() or singleton() calls with no custom construction logic.
- **Should** Give each domain module a service provider that registers its bindings and loads its routes, configuration, and other resources. — score 5: [Mateus](https://www.youtube.com/watch?v=WqL6wgH1fKs) (Laracon speaker, 2); [Ryuta Hamasaki](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=4011s) (Laracon speaker, 2); [Mateus Guimarães](https://laracasts.com/episodes/3029) (Tier 3, 1)
  - Why: makes module integration explicit and keeps registration with the owning module.
  - Flag when: Module resources or bindings are scattered across unrelated application registration files.
- **Should** Provide documented, repeatable commands for setup, dev, tests, formatting, and deploy, plus useful seed data. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/sail) (Official, 3); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk&t=1560s) (Laracon speaker, 2)
  - Why: lets new developers get a fresh checkout running quickly with working tests and representative data.
  - Flag when: New setup requirements or required services lack corresponding setup commands or documentation.
- **Should** Replace legacy request paths incrementally behind a defined bridge while preserving existing user workflows. — score 5: [James Brooks](https://www.youtube.com/watch?v=he2-4Dbc-y0) (Laracon speaker (employee), 3); [Jordan Havard](https://www.youtube.com/watch?v=riJBa0Bxo-8) (Laracon speaker, 2)
  - Why: reduces migration risk and permits old and new behavior to coexist until replacement is verified.
  - Flag when: A replacement removes working legacy paths or changes required user behavior before equivalent routes are ready.
- **Should** Review your own diff and get CI green before requesting review; get a second developer's eyes on every change. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/pint) (Official, 3); [Luke Kuzmish](https://www.youtube.com/watch?v=cucIWpAenro&t=23273s) (Laracon speaker, 2)
  - Why: keeps repetitive mechanical fixes out of human reviews and brings another developer’s perspective.
- **Should** Separate event-derived domain state from read projections and make projections safely rebuildable from retained events. — score 4: [Daniel Coulbourne](https://www.youtube.com/watch?v=tX6nBpSvh4s) (Laracon speaker, 2); [Spatie](https://spatie.be/docs/laravel-event-sourcing/v7/getting-familiar-with-event-sourcing/introduction) (Tier 2, 2)
  - Why: allows projection corrections and schema changes without guessing lost history.
  - Flag when: Projection handlers depend on unrecoverable mutable data or replay duplicates rows without reset or idempotency.
- **Should** Separate replayable state and projection updates from one-time side effects, and suppress those effects during replay. — score 4: [Daniel Coulbourne](https://www.youtube.com/watch?v=tX6nBpSvh4s) (Laracon speaker, 2); [Spatie](https://spatie.be/docs/laravel-event-sourcing/v7/using-reactors/writing-your-first-reactor) (Tier 2, 2)
  - Why: prevents reconstruction from sending duplicate messages or invoking external services again.
  - Flag when: Event replay can resend emails, payments, downstream events, or third-party requests.
- **Should** Use Laravel’s scheduler for periodic cleanup and time-based state updates instead of defining a separate cron entry for each task. — score 4: [Josh Cirre](https://laracasts.com/episodes/3337) (Tier 1, 3); [Andre Madarang](https://laracasts.com/episodes/2528) (Tier 3, 1)
  - Why: keeps recurring application work centrally configured and maintained.
  - Flag when: A periodic application task adds its own cron entry or relies on page visits to refresh time-based state.
- **Should** Validate event-sourced workflow transitions against aggregate or domain state before accepting and applying events. — score 4: [Daniel Coulbourne](https://www.youtube.com/watch?v=-mb2L97Yq88) (Laracon speaker, 2); [Spatie](https://spatie.be/docs/laravel-event-sourcing/v7/getting-familiar-with-event-sourcing/introduction) (Tier 2, 2)
  - Why: prevents invalid operations from becoming part of the authoritative event history.
  - Flag when: An event is accepted without checking the current workflow state or domain invariants.
- **Consider** Centralize a recipient’s notification and mail locale preference on the notifiable model when recipient-specific localization is required. — score 3: [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3)
  - Why: makes localized delivery consistent across notification paths.
  - Flag when: Notification callers repeatedly select a recipient locale instead of using a shared preference.
- **Consider** Choose Livewire or an Inertia-backed JavaScript stack for interactive pages according to the application and team’s needs. — score 3: [Taylor Otwell](https://x.com/taylorotwell/status/1570777261342883840) (Tier 1, 3)
  - Why: provides an established interactive UI approach that fits how the team builds pages.
  - Flag when: A new interactive page invents custom client-server plumbing where the chosen application stack already provides it.
- **Consider** Document team conventions (naming, structure, branching, review) and enforce formatting with Pint. — score 3: [Laravel (official)](https://laravel.com/docs/13.x/structure) (Official, 3)
  - Why: makes recurring implementations predictable and applies shared conventions consistently.
- **Consider** Handle request-wide presentation concerns in middleware and share their resolved values with views. — score 3: [Laravel (official)](https://github.com/laravel/react-starter-kit/blob/717b8f55aefd82d25d4119eaebdc8e3a72b8d7e5/app/Http/Middleware/HandleAppearance.php#L10-L21) (Official, 3)
  - Why: avoids repeating cookie or preference resolution in each controller or template.
  - Flag when: Multiple entry points independently resolve the same request-wide presentation preference.
- **Consider** Limit service-provider register() methods to container bindings; register routes, listeners, and other functionality in boot(). — score 3: [Laravel (official)](https://laravel.com/docs/13.x/providers#writing-service-providers) (Official, 3)
  - Why: avoids using functionality before all providers have registered their dependencies.
  - Flag when: A register() method registers routes or listeners or relies on another provider’s booted functionality.
- **Consider** Send notifications to arbitrary recipients through on-demand routing rather than creating dummy persisted models. — score 3: [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3)
  - Why: avoids artificial records solely to supply a notification destination.
  - Flag when: A notification flow creates a dummy user or model just to send to an address.
- **Consider** Use Laravel listener discovery for conventional listeners and configure discovery paths when their location changes. — score 3: [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3)
  - Why: avoids redundant listener wiring while keeping listeners in custom layouts discoverable.
  - Flag when: A listener moves outside discovery paths without corresponding discovery configuration.
- **Consider** Use the agreed business vocabulary consistently across operations, events, code, and docs. — score 3: [Laravel (official)](https://laravel.com/docs/13.x/eloquent) (Official, 3)
  - Why: preserves shared understanding between developers and domain experts as terminology evolves.
  - Flag when: A renamed business concept retains conflicting names in related operations, events, or documentation.

  - Why: recorded intent helps maintain consistent responsive behavior.
  - Flag when: Custom breakpoint choices added without an explanation.
- **Consider** Prefer native select controls when they meet the required styling, interaction, and browser-support needs. — score 2: [Spatie](https://spatie.be/blog/rethinking-our-frontend-future-at-spatie) (Tier 2, 2)
  - Why: native controls can avoid unnecessary custom dropdown dependencies.
  - Flag when: Custom dropdown dependency introduced for needs a native select can meet.
- **Consider** Prefer rem-based breakpoints when layouts should respond to user font-size preferences. — score 2: [Spatie](https://spatie.be/blog/can-we-make-default-tailwind-a-more-accessible-choice) (Tier 2, 2)
  - Why: relative breakpoints accommodate larger preferred font sizes.
  - Flag when: New or changed breakpoints expressed in fixed pixel units.
- **Consider** Verify responsive layouts with different browser default font sizes. — score 2: [Spatie](https://spatie.be/blog/can-we-make-default-tailwind-a-more-accessible-choice) (Tier 2, 2)
  - Why: font-size changes can expose breakpoint and layout failures.
  - Flag when: Responsive layout changes without checking larger default font sizes.

## Package building

### Packages

- **Must** Document the install command, usage examples, and how to run tests and contribute. — score 8: [Laravel (official)](https://laravel.com/docs/13.x/packages) (Official, 3); [Nuno Maduro](https://x.com/enunomaduro/status/1857805873017389324) (Tier 1, 3); [Spatie](https://freek.dev/2558-workbench-app-for-packages) (Tier 2, 2)
  - Why: consumers and future maintainers need usable instructions without knowing the package internals.
  - Flag when: Documented installation commands or usage examples contradict the changed package API.
- **Must** Test framework-dependent packages with Orchestra Testbench, loading providers and migrations explicitly. — score 7: [Laravel (official)](https://laravel.com/docs/13.x/packages) (Official, 3); [Kath Young](https://www.youtube.com/watch?v=blUswpYpmIs&t=725s) (Laracon speaker, 2); [Spatie](https://freek.dev/2558-workbench-app-for-packages) (Tier 2, 2)
  - Why: bare PHPUnit tests lack the Laravel services and database schema needed by framework-dependent package behavior.
  - Flag when: Framework-dependent package tests extend bare PHPUnit TestCase without bootstrapping Laravel.
- **Should** Register package resources through its service provider, using boot() for runtime components and centralized resource declarations when package tooling supports them. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/blade#manually-registering-package-components) (Official, 3); [Spatie](https://github.com/spatie/laravel-package-tools) (Tier 2, 2)
  - Why: consistent provider registration makes package resources available and avoids duplicated setup plumbing.
  - Flag when: Package resources are unregistered, runtime components are registered before boot, or resource declarations bypass the package provider conventions.
- **Should** Start packages from a current skeleton (e.g. Spatie's package skeleton) with clear src/tests namespaces. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/packages) (Official, 3); [Spatie](https://freek.dev/2442-strategies-for-making-laravel-packages-customizable) (Tier 2, 2)
  - Why: a skeleton supplies package namespaces, Composer metadata, providers, and test setup before feature work.
- **Should** Use Spatie Laravel Data where it removes duplicated shapes, keeping validation explicit. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/validation) (Official, 3); [Spatie](https://www.youtube.com/watch?v=CrO_7Df1cBc&t=210s) (Laracon speaker, 2)
  - Why: one typed definition reduces repeated schemas across request validation, API responses, and frontend types.
- **Should** Use scoped route discovery only for repetitive routes, keeping manual routes where control matters. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/routing) (Official, 3); [Spatie](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=28080s) (Laracon speaker, 2)
  - Why: scoped discovery removes repetitive declarations while manual routes preserve deliberate control over important URLs.
  - Flag when: Route discovery scans all controllers or views instead of a dedicated directory.
- **Should** Build reusable components inside the app first, then extract mature ones into packages (Composer path repositories). — score 4: [Matt Stauffer](https://www.youtube.com/watch?v=f4QShF42c6E&t=13999s) (Laracon speaker, 2); [Spatie](https://www.youtube.com/watch?v=Boqfw4ZCk7g) (Laracon speaker, 2)
  - Why: mature, separable features can be reused and maintained independently while the application stays focused on its domain.
- **Should** Expose focused extension points and configurable default classes for customizable package operations, models, and jobs; consistently use the configured implementations. — score 4: [Dan Harrin](https://www.youtube.com/watch?v=cucIWpAenro&t=3257s) (Laracon speaker, 2); [Spatie](https://freek.dev/2442-strategies-for-making-laravel-packages-customizable) (Tier 2, 2)
  - Why: consumers can customize individual steps and types without copying workflows or editing vendor code.
  - Flag when: Customizable workflows are monolithic, narrow configuration switches multiply, or package code bypasses configured model, action, or job classes.
- **Consider** Avoid naming third-party packages or products "Laravel X" in a way that implies official Laravel ownership. — score 3: [Taylor Otwell](https://x.com/taylorotwell/status/1620807927715217409) (Tier 1, 3)
  - Why: the Laravel trademark and product identity should not imply endorsement of third-party offerings.
  - Flag when: A third-party package or product adopts a Laravel-prefixed brand suggesting it is an official Laravel product.
- **Consider** Capture reusable project defaults in a starter kit with an .env.example and automated Composer project-creation setup. — score 3: [Josh Cirre](https://www.youtube.com/watch?v=RY6wrHaLeCo) (Laracon speaker (employee), 3)
  - Why: repeatable project initialization keeps shared defaults and setup steps consistent.
  - Flag when: A starter kit omits environment templates or requires manual setup that should run during project creation.
- **Consider** Follow semantic versioning and keep a changelog and upgrade guide. — score 3: [Laravel (official)](https://laravel.com/docs/13.x/releases) (Official, 3)
  - Why: predictable versions and migration instructions help consumers understand release changes and upgrade requirements.
- **Consider** Implement package logic in plain services; register providers and optional facades via Composer auto-discovery. — score 3: [Laravel (official)](https://laravel.com/docs/13.x/facades) (Official, 3)
  - Why: an optional facade proxies an ordinary service that consumers can also instantiate directly.
  - Flag when: Package business logic is implemented inside a facade instead of its underlying service.
- **Consider** Keep API docs current: purpose, auth, parameters, validation, responses, and error examples. — score 3: [James Brooks](https://www.youtube.com/watch?v=K-g-t99mKZU&t=480s) (Laracon speaker (employee), 3)
  - Why: code-derived documentation and explicit examples help consumers understand endpoint contracts beyond successful responses.
  - Flag when: Changed authentication, validation, or response behavior contradicts endpoint documentation or examples.
- **Consider** Keep package changes compatible with the declared supported Laravel versions and verify that range with framework integration tests. — score 3: [Mior Muhammad Zaki](https://x.com/crynobone/status/1767036099757846748) (Tier 1, 3)
  - Why: consumers on supported framework versions should continue receiving working package releases.
  - Flag when: New framework APIs exceed Composer constraints or integration tests cover only part of the declared supported Laravel range.
- **Consider** Keep runtime deps in `require` and tools/tests in `require-dev`/`autoload-dev`. — score 3: [Laravel (official)](https://laravel.com/docs/13.x/packages#service-providers) (Official, 3)
  - Why: consumers receive runtime dependencies without inheriting package test tooling or test autoload mappings.
  - Flag when: Composer.json puts test tools in require, test namespaces in autoload, or runtime dependencies in require-dev.
- **Consider** Use a maintained media package (e.g. Spatie Media Library) with purpose-specific collections and disks. — score 3: [Laravel (official)](https://laravel.com/docs/13.x/filesystem) (Official, 3)
  - Why: a media package handles repeated upload, model association, derivative, and storage workflows.
- **Consider** Verify Cashier webhook signatures, trust provider state for orders and subscriptions, and keep custom effects in listeners. — score 3: [Laravel (official)](https://laravel.com/framework/docs/13.x/billing#defining-webhook-event-handlers) (Official, 3)
  - Why: authenticated provider callbacks establish billing state while asynchronous checkout completion may still be pending.
  - Flag when: Checkout return handlers mark orders paid without provider confirmation, or webhook routes bypass signature verification.
- **Consider** Dispatch contextual events at meaningful package lifecycle points so consumers can attach side effects through listeners. — score 2: [Spatie](https://www.youtube.com/watch?v=uZU1F_BWiXU) (Laracon speaker, 2)
  - Why: application-specific side effects can extend package behavior without changing package internals.
  - Flag when: Package lifecycle side effects require editing internal workflows or adding a separate configuration switch for each consumer hook.
- **Consider** Protect package registry accounts with two-factor authentication and create release tags only from the protected release branch. — score 2: [Spatie](https://spatie.be/guidelines/secure-coding) (Tier 2, 2)
  - Why: protected publishing credentials and reviewed release commits reduce unauthorized package releases.
  - Flag when: Release workflows tag unprotected branches or documented registry account policies omit two-factor authentication.
- **Consider** Provide an installation command when package setup requires multiple coordinated actions. — score 2: [Spatie](https://github.com/spatie/laravel-package-tools) (Tier 2, 2)
  - Why: one repeatable entry point reduces incomplete or inconsistent consumer setup.
  - Flag when: Package installation requires coordinated manual setup steps with no command to perform them.
