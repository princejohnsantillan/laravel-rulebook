# Laravel Infra Rules

**Version:** 2026-10-13 18:19 (Asia/Manila)

**Scope:** Running Laravel 13 apps: deployment, CI/CD, scaling and Octane, queues, caching, database operations, observability, and security operations.

**Levels:** **Must** = score 7+ · **Should** = score 4–6 · **Consider** = score 2–3. Score = sum of points from independent sources (official 3, tier 1 3, Laracon speaker 2 or 3 for employees, tier 2 2–3, tier 3 1).

**Sub-bullets:** *Why* = the reason behind the rule, quotable when flagging a violation · *Flag when* = an observable signal in a diff that suggests a violation (omitted when not observable in code).

*Written for code-reviewing agents: use these rules to evaluate diffs, not as an implementation checklist.*

*Each rule lists its score and every independent source (tier, points).*

**Known limitations of this version:**
- Tier 2 was built from the following lists of tier 1 accounts, and X truncated those lists, so some accounts followed by 5+ employees may be missing from tier 2.
- Paid Laracasts episodes were covered from their public descriptions and lesson notes only, not full transcripts.
- Rules extracted from blogs (Securing Laravel, aaronfrancis.com, Spatie, Tighten, freek.dev and others) are machine summaries of each article, not direct quotes; follow the link before quoting.
- Official sources (Laravel docs, Boost, first-party code, Pint/Larastan, product docs) count as one org; Spatie and Freek count as one org; each person counts once per rule at the highest tier among their evidence for that rule.

## Infrastructure

### Deployment

- **Must** Deploy unfinished or replacement functionality behind feature gates; increase user exposure in monitored cohorts and retain a quick disable path. — score 19: [Aaron Francis](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=12420s) (Laracon speaker (employee), 3); [James Brooks](https://www.youtube.com/watch?v=he2-4Dbc-y0) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Daniel Coulbourne](https://www.youtube.com/watch?v=OpCT3s4wTI0) (Laracon speaker, 2); [James Mooring](https://www.youtube.com/watch?v=hpUrWWlBKCY) (Laracon speaker, 2); [John Drexler](https://www.youtube.com/watch?v=YJmuKPk3d9M&t=11255s) (Laracon speaker, 2); [Ryan Lovett](https://www.youtube.com/watch?v=AJ8MOFoDeP0) (Laracon speaker, 2); [Sam Sehnert](https://www.youtube.com/watch?v=IPbxscS0xiY) (Laracon speaker, 2)
  - Why: controlled exposure limits the impact of regressions while allowing incremental delivery.
  - Flag when: A release enables unfinished or replacement functionality for all users without a feature gate or staged rollout.
- **Must** Define reproducible runtimes (PHP version, extensions, services) and keep data independent of rebuildable containers. — score 14: [Aaron Francis](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=11684s) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/sail) (Official, 3); [Francesco Ciulla](https://www.youtube.com/watch?v=CMqhOhRnOY0&t=150s) (Laracon speaker, 2); [Justin Reasoner](https://www.youtube.com/watch?v=DdMFP_K0gv4) (Laracon speaker, 2); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk) (Laracon speaker, 2); [Ryan Lovett](https://www.youtube.com/watch?v=AJ8MOFoDeP0) (Laracon speaker, 2)
  - Why: prevents runtime mismatches and repeated manual environment setup.
  - Flag when: Container rebuild deletes the only copy of database data.
- **Must** Automate tested releases with health checks, atomic or blue-green/canary rollout, rollback paths, and post-release error and latency checks. — score 11: [Laravel (official)](https://laravel.com/forge/docs/sites/deployments) (Official, 3); [Bosun Egberinde](https://www.youtube.com/watch?v=f4QShF42c6E&t=3332s) (Laracon speaker, 2); [Neel Shah](https://www.youtube.com/watch?v=CdfW-bCKZ3E) (Laracon speaker, 2); [Ryan Lovett](https://www.youtube.com/watch?v=AJ8MOFoDeP0) (Laracon speaker, 2); [Jeffrey Way](https://laracasts.com/episodes/3911) (Tier 3, 1); [Matt Stauffer](https://laracasts.com/episodes/3776) (Tier 3, 1)
  - Why: enables rapid recovery to a previous release when deployment fails.
  - Flag when: Deployment pipeline removes test gates or rollback steps.
- **Must** Build dependencies and assets from a versioned commit into an immutable release, separate from deploy, and reload processes to activate it; never edit production code in place. — score 10: [Aaron Francis](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=11684s) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Justin Reasoner](https://www.youtube.com/watch?v=DdMFP_K0gv4&t=150s) (Laracon speaker, 2); [Sam Sehnert](https://www.youtube.com/watch?v=IPbxscS0xiY) (Laracon speaker, 2)
  - Why: rebuilding alone leaves old code running until deployed processes are replaced or reloaded.
  - Flag when: Deployment rebuilds an image without updating or restarting running application instances.
- **Must** Prepare config, route, event, and view caches for production as part of the release pipeline once the target configuration is available; avoid config caching during routine local development. — score 10: [Laravel (official)](https://laravel.com/docs/13.x/configuration#configuration-caching) (Official, 3); [Nuno Maduro](https://x.com/enunomaduro/status/1564273701683617792) (Tier 1, 3); [Marcel Pociot](https://www.youtube.com/watch?v=rk29Hyk59JY) (Laracon speaker, 2); [Spatie](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=27816s) (Laracon speaker, 2)
  - Why: prepared caches reduce repeated framework work and must reflect the target environment.
  - Flag when: The production release pipeline omits framework cache preparation or prepares config caches before target environment values are available.
- **Must** Use a managed platform (Laravel Cloud, Forge, Vapor) when it cuts operating effort at acceptable cost. — score 10: [Devon Garbalosa](https://www.youtube.com/watch?v=toSMnEINXAo) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [James Mooring](https://www.youtube.com/watch?v=hpUrWWlBKCY) (Laracon speaker, 2); [Spatie](https://spatie.be/blog/our-hackathon-project-live-at-spatie) (Tier 2, 2)
  - Why: reduces the setup and maintenance effort needed for deployment automation.
- **Must** Supervise persistent application processes with automatic restarts and configure their proxies and connection limits for the expected workload. — score 9: [Joe Dixon](https://www.youtube.com/watch?v=IDYzAMDs2YI) (Laracon speaker (employee), 3); [Joe Tannenbaum](https://blog.joe.codes/creating-ssh-apps-with-charm-wish-and-laravel-prompts) (Tier 1, 3); [Laravel (official)](https://laravel.com/docs/13.x/deployment#reloading-services) (Official, 3)
  - Why: long-running services need recovery after failure and sufficient connection capacity.
  - Flag when: Persistent application processes lack a supervisor, restart policy, or required proxy and connection-limit configuration.
- **Must** Evaluate Octane (FrankenPHP, Swoole, RoadRunner) against your workload before adopting it. — score 7: [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Kévin Dunglas](https://www.youtube.com/watch?v=PzOLyz1vr5I&t=180s) (Laracon speaker, 2); [Mateus Guimarães](https://www.youtube.com/watch?v=dOXXL-98Zbs) (Laracon speaker, 2)
  - Why: reduces repeated framework boot overhead where persistent workers benefit the workload.
- **Must** Isolate production, staging, and preview environments with separate configuration, secrets, resources, and deployment settings. — score 7: [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3); [Mohamed Said](https://laracasts.com/episodes/2614) (Tier 1, 3); [Stephen Rees-Carter](https://securinglaravel.com/in-depth-securing-apps-on-forge) (Tier 3, 1)
  - Why: environment isolation prevents test activity or configuration changes from affecting production.
  - Flag when: Non-production and production deployments share credentials or mutable backing resources without deliberate isolation.
- **Must** Keep config and secrets out of code, and reload consumers after changing them. — score 7: [Laravel (official)](https://laravel.com/docs/13.x/database) (Official, 3); [Francesco Ciulla](https://www.youtube.com/watch?v=CMqhOhRnOY0) (Laracon speaker, 2); [Matt Stauffer](https://laracasts.com/episodes/3778) (Tier 3, 1); [Stephen Rees-Carter](https://securinglaravel.com/in-depth-securing-apps-on-forge) (Tier 3, 1)
  - Why: allows service endpoints and credentials to change without source edits.
  - Flag when: Application code hard-codes deployment credentials or backing-service endpoints.
- **Should** Build assets with Vite (hashed filenames, consistent `ASSET_URL`) and give only versioned URLs long cache lifetimes. — score 6: [Laravel (official)](https://laravel.com/docs/13.x/vite#custom-base-urls) (Official, 3); [Mohamed Said](https://laracasts.com/episodes/2666) (Tier 1, 3)
  - Why: keeps changed assets fresh while allowing unchanged assets to remain cached.
  - Flag when: Long cache lifetimes applied to asset URLs without content versioning.
- **Should** Keep Laravel and PHP on supported, compatible versions and plan regular framework and runtime upgrades. — score 6: [Laravel (official)](https://laravel.com/cloud/docs/deployments) (Official, 3); [Pascal Baljet](https://x.com/pascalbaljet/status/1706644796947792298) (Tier 1, 3)
  - Why: maintained compatible versions retain security fixes and reduce upgrade backlog.
  - Flag when: A deployment pins an unsupported Laravel or PHP version or introduces an incompatible runtime upgrade.
- **Should** Use multi-stage production images with only runtime artifacts; exclude compilers, dev deps, and Sail. — score 6: [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Francesco Ciulla](https://www.youtube.com/watch?v=CMqhOhRnOY0&t=690s) (Laracon speaker, 2); [Stephen Rees-Carter](https://securinglaravel.com/security-tip-disable-dev-tools-on) (Tier 3, 1)
  - Why: reduces production image size by leaving build tools and test dependencies behind.
  - Flag when: Final production image includes compilers, development dependencies, or Sail tooling.
- **Should** Allow only key-based SSH for authorized users and firewall everything but required ports (IPv4 and IPv6). — score 5: [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Chris Fidao](https://www.youtube.com/watch?v=f4QShF42c6E&t=30221s) (Laracon speaker, 2)
  - Why: restricts server access to authorized users and required inbound traffic.
  - Flag when: SSH config enables password login or firewall config allows unnecessary inbound ports.
- **Should** Choose a trusted minimal PHP base image after verifying versions, extensions, and libc compatibility. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Francesco Ciulla](https://www.youtube.com/watch?v=CMqhOhRnOY0&t=630s) (Laracon speaker, 2)
  - Why: reduces image size while retaining required extensions and compatible runtime libraries.
- **Should** Gate startup on application-level readiness checks, not open ports or start order. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/artisan) (Official, 3); [Justin Reasoner](https://www.youtube.com/watch?v=DdMFP_K0gv4) (Laracon speaker, 2)
  - Why: prevents dependent operations from running before required services are ready.
  - Flag when: Startup runs migrations after only a port check or unconditional service start.
- **Should** Ship structured logs from every host and process (stdout/stderr) to a searchable destination. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/octane) (Official, 3); [Kévin Dunglas](https://www.youtube.com/watch?v=PzOLyz1vr5I&t=660s) (Laracon speaker, 2)
  - Why: makes access and operational events auditable across hosts.
  - Flag when: Production logging switches to uncollected local files or discards process output.
- **Should** Use Sail or an equivalent container dev setup with wrappers for PHP, Composer, Artisan, and asset commands. — score 5: [Laravel (official)](https://laravel.com/docs/13.x/sail) (Official, 3); [Francesco Ciulla](https://www.youtube.com/watch?v=CMqhOhRnOY0&t=810s) (Laracon speaker, 2)
  - Why: runs development commands with the application’s actual PHP runtime and dependencies.
- **Should** Automate ordered release steps (env setup, `storage:link`, migrations) using the release's own code and config. — score 4: [Laravel (official)](https://laravel.com/docs/13.x/artisan) (Official, 3); [Matt Stauffer](https://laracasts.com/episodes/3770) (Tier 3, 1)
  - Why: release tasks need the deployed code and configuration to operate against the intended application environment.
  - Flag when: Deployment runs migrations before environment setup or from a different release directory.
- **Should** Configure APP_URL and the production primary domain to the intended canonical application URL. — score 4: [Laravel (official)](https://laravel.com/docs/13.x/mcp#client-metadata) (Official, 3); [Matt Stauffer](https://laracasts.com/episodes/3777) (Tier 3, 1)
  - Why: correct canonical URLs keep generated links and redirects on the intended production domain.
  - Flag when: Production APP_URL or primary-domain configuration points to a temporary or incorrect host.
- **Should** Declare application listeners and service routing explicitly, and connect containers through stable service names rather than instance IP addresses. — score 4: [Francesco Ciulla](https://www.youtube.com/watch?v=CMqhOhRnOY0) (Laracon speaker, 2); [Justin Reasoner](https://www.youtube.com/watch?v=DdMFP_K0gv4) (Laracon speaker, 2)
  - Why: consistent service discovery and port routing survive instance replacement.
  - Flag when: Container clients use instance IP addresses or service selectors and target ports do not match the application workload.
- **Should** Refresh published vendor assets when upgrading dependencies that require publishing, and automate this in the update workflow. — score 4: [Laravel (official)](https://laravel.com/docs/13.x/telescope#upgrading-telescope) (Official, 3); [Luke Downing](https://laracasts.com/episodes/2863) (Tier 3, 1)
  - Why: stale published assets can become incompatible with upgraded package code.
  - Flag when: A dependency upgrade leaves required published vendor assets stale or omits its asset refresh step.
- **Consider** Configure a cron entry to run php artisan schedule:run every minute when using cron to trigger Laravel's scheduler. — score 3: [Mohamed Said](https://laracasts.com/episodes/2752) (Tier 1, 3)
  - Why: a single scheduler entry lets application code control task timing.
  - Flag when: Cron deployment omits schedule:run or creates separate cron entries for individual Laravel scheduled tasks.
- **Consider** Grant the application runtime permission to write to storage and bootstrap/cache. — score 3: [Laravel (official)](https://laravel.com/docs/13.x/deployment#directory-permissions) (Official, 3)
  - Why: the framework needs writable runtime and cache directories to operate.
  - Flag when: Deployment ownership or permissions prevent the application process from writing to storage or bootstrap/cache.
- **Consider** Group scheduled tasks when they genuinely share frequency or execution constraints. — score 3: [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3)
  - Why: shared schedule definitions keep related task constraints consistent.
  - Flag when: Several related scheduled tasks duplicate the same frequency and constraints with inconsistent settings.
- **Consider** Maintain infrastructure code in a version-controlled repository separate from application repositories. — score 3: [Mohamed Said](https://laracasts.com/episodes/2952) (Tier 1, 3)
  - Why: independent infrastructure versioning supports reusable and controlled operational changes.
  - Flag when: Infrastructure definitions are embedded in application repositories rather than maintained in a separate infrastructure repository.
- **Consider** Place application compute and backing resources in the same region where practical. — score 3: [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3)
  - Why: regional proximity reduces network latency and cross-region traffic.
  - Flag when: Application compute and frequently accessed backing resources are deployed in different regions without a stated requirement.
- **Consider** Prefer timezone-independent scheduling; account for skipped or repeated executions when local-time schedules are necessary. — score 3: [Laravel (official)](https://laravel.com/docs/13.x/scheduling#timezones) (Official, 3)
  - Why: daylight-saving transitions can skip tasks or execute them twice.
  - Flag when: A timezone-based schedule assumes each local time occurs exactly once without handling daylight-saving transitions.
- **Consider** Restrict environment-specific scheduled tasks to their intended application environments. — score 3: [Laravel (official)](https://github.com/laravel/boost/tree/main/.ai) (Official, 3)
  - Why: environment constraints prevent inappropriate jobs from running in other deployments.
  - Flag when: A production-only or staging-only scheduled task has no environment restriction.
- **Consider** Upload files that exceed application request limits directly to object storage using authorized client uploads. — score 3: [Laravel (official)](https://docs.vapor.build/resources/storage) (Official, 3)
  - Why: direct uploads avoid routing oversized request bodies through constrained application servers.
  - Flag when: Uploads exceeding backend request limits are routed through the application rather than an authorized direct-storage upload path.
- **Consider** Declare infrastructure desired state in an authoritative source and reconcile resources against it with repeatable, retry-safe operations. — score 2: [Chris Fidao](https://www.youtube.com/watch?v=fymjefGMUas) (Laracon speaker, 2)
  - Why: declarative reconciliation repairs drift and makes infrastructure reproducible.
  - Flag when: Infrastructure controllers use conflicting desired-state sources, omit drift reconciliation, or duplicate side effects on retries.
- **Consider** Keep legacy data projections current during incremental migration and retire the legacy system only after a sufficient observation period. — score 2: [Daniel Coulbourne](https://www.youtube.com/watch?v=OpCT3s4wTI0) (Laracon speaker, 2)
  - Why: continued synchronization preserves fallback options until the replacement is proven.
  - Flag when: A migration stops legacy synchronization or removes the legacy system before replacement behavior has been observed in production.

### CI/CD

- **Must** Enforce style and static analysis on new code automatically and baseline legacy violations to reduce over time. — score 17: [Ashley Hindle](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=33720s) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/pint) (Official, 3); [Nuno Maduro](https://x.com/enunomaduro/status/1772766509330235722) (Tier 1, 3); [Lucas Giovanny](https://www.youtube.com/watch?v=PWV5b0sL5Wo) (Laracon speaker, 2); [Sam Sehnert](https://www.youtube.com/watch?v=IPbxscS0xiY&t=840s) (Laracon speaker, 2); [Tighten](https://tighten.com/insights/automated-refactoring-with-rector-php) (Tier 2, 2); [Luke Downing](https://laracasts.com/episodes/3388) (Tier 3, 1); [Mateus Guimarães](https://laracasts.com/episodes/3604) (Tier 3, 1)
  - Why: introduces automated checks without requiring a complete legacy cleanup first.
  - Flag when: CI disables style or static analysis checks, or baselines new violations.
- **Must** Run tests, style, static analysis, and builds in CI and require them to pass (plus an approved PR) before merge and release. — score 14: [Ashley Hindle](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=31692s) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/testing) (Official, 3); [James Mooring](https://www.youtube.com/watch?v=hpUrWWlBKCY) (Laracon speaker, 2); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk) (Laracon speaker, 2); [Sam Sehnert](https://www.youtube.com/watch?v=IPbxscS0xiY) (Laracon speaker, 2); [Jason McCreary](https://laracasts.com/episodes/2703) (Tier 3, 1); [Luke Downing](https://laracasts.com/episodes/3389) (Tier 3, 1)
  - Why: prevents faulty changes from reaching production.
  - Flag when: CI deploys after failed checks or skips executing test targets.
- **Must** Integrate and deploy small increments frequently. — score 12: [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Sam Rose](https://x.com/samwhoo/status/1847202638556754174) (Tier 1, 3); [John Drexler](https://www.youtube.com/watch?v=YJmuKPk3d9M&t=11255s) (Laracon speaker, 2); [Matt Stauffer](https://www.youtube.com/watch?v=KBigS5vLwZk) (Laracon speaker, 2); [Sam Sehnert](https://www.youtube.com/watch?v=IPbxscS0xiY&t=420s) (Laracon speaker, 2)
  - Why: reduces merge conflicts, deployment risk, and feedback delay.
- **Must** Centralize deploy and ops actions in a visible shared tool or bot. — score 8: [Laravel (official)](https://laravel.com/docs/13.x/deployment) (Official, 3); [Mohamed Said](https://laracasts.com/episodes/2758) (Tier 1, 3); [James Mooring](https://www.youtube.com/watch?v=hpUrWWlBKCY&t=971s) (Laracon speaker, 2)
  - Why: makes deployments repeatable instead of depending on individual developers’ machines.
- **Must** Favor meaningful feature and integration tests over chasing a coverage number. — score 8: [Ashley Hindle](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=33510s) (Laracon speaker (employee), 3); [Laravel (official)](https://laravel.com/docs/13.x/testing) (Official, 3); [Sam Sehnert](https://www.youtube.com/watch?v=IPbxscS0xiY&t=990s) (Laracon speaker, 2)
  - Why: meaningful behavior tests provide useful feedback without pursuing an arbitrary coverage target.
- **Should** Pin third-party CI actions and fetched workflow dependencies to verified immutable revisions and grant workflows only necessary permissions. — score 6: [Laravel (official)](https://github.com/laravel/react-starter-kit/blob/717b8f55aefd82d25d4119eaebdc8e3a72b8d7e5/.github/workflows/tests.yml#L17-L38) (Official, 3); [Spatie](https://spatie.be/guidelines/secure-coding) (Tier 2, 2); [Stephen Rees-Carter](https://securinglaravel.com/in-depth-version-numbers-are-vanity-labels) (Tier 3, 1)
  - Why: verified immutable references and narrow permissions reduce supply-chain exposure.
  - Flag when: Actions use mutable tags, fetched references lack authenticity checks, or workflow permissions exceed job needs.
- **Should** Keep CI feedback fast by caching dependencies and removing unnecessary work while retaining required checks. — score 5: [Owen Conti](https://springloaded.co/blog/turbocharge-your-laravel-tests-on-github-actions) (Tier 2, 2); [Sam Sehnert](https://www.youtube.com/watch?v=IPbxscS0xiY) (Laracon speaker, 2); [Luke Downing](https://laracasts.com/episodes/3391) (Tier 3, 1)
  - Why: short feedback cycles support frequent integration and delivery.
  - Flag when: CI repeatedly installs uncached dependencies or adds redundant setup and checks.
- **Should** Review your own pull request, confirm CI passes, and provide testing instructions and implementation reasoning before requesting review. — score 5: [Ashley Hindle](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=31692s) (Laracon speaker (employee), 3); [Luke Kuzmish](https://www.youtube.com/watch?v=cucIWpAenro&t=23273s) (Laracon speaker, 2)
  - Why: reviewers can evaluate behavior and design with sufficient context.
  - Flag when: Pull requests request review with failing checks or omit needed testing instructions and reasoning.
- **Should** Generate coverage reports in CI and enforce any agreed minimum coverage threshold. — score 4: [Nuno Maduro](https://www.youtube.com/watch?v=328A3aFOy6M) (Laracon speaker (employee), 3); [Luke Downing](https://laracasts.com/episodes/3394) (Tier 3, 1)
  - Why: coverage reports and agreed thresholds reveal test gaps and coverage regressions.
  - Flag when: CI omits coverage reporting or bypasses the agreed minimum.
- **Consider** Audit application dependencies for vulnerabilities in CI and on a recurring schedule, failing checks for vulnerabilities covered by the project policy. — score 3: [Spatie](https://freek.dev/2892-how-to-monitor-your-laravel-app-for-critical-vulnerabilities) (Tier 2, 2); [Stephen Rees-Carter](https://securinglaravel.com/security-tip-composer-audit) (Tier 3, 1)
  - Why: recurring checks catch vulnerabilities disclosed after a release.
  - Flag when: Dependency audits are absent, bypassed, or run only when dependencies change.
- **Consider** Balance large CI test suites across shards using measured test durations and keep timing data current. — score 3: [Nuno Maduro](https://www.youtube.com/watch?v=71bMyZcDlM4) (Laracon speaker (employee), 3)
  - Why: duration-based distribution reduces slow shards and feedback time.
  - Flag when: Large suites are sharded by file count despite uneven runtimes or use stale timing data.
- **Consider** Install CI dependencies from committed lockfiles, provision required application configuration, and test supported runtime and framework versions. — score 3: [Laravel (official)](https://github.com/laravel/laravel/blob/f4000aeb018fcbf71d4a13e3ee4b80c7e2d45be5/.github/workflows/tests.yml#L22-L49) (Official, 3)
  - Why: reproducible setup and compatibility testing expose environment-dependent failures.
  - Flag when: CI updates dependencies instead of installing locked versions, omits required test setup, or tests unsupported version combinations.
- **Consider** Regenerate API documentation and response fixtures automatically and publish client-facing API artifacts through CI. — score 3: [James Brooks](https://www.youtube.com/watch?v=K-g-t99mKZU) (Laracon speaker (employee), 3)
  - Why: generated artifacts stay consistent with the implementation.
  - Flag when: API changes leave generated documentation or response fixtures stale.
- **Consider** Use staging for release QA and automate staging and production deployments when their designated branches are merged. — score 3: [Ashley Hindle](https://www.youtube.com/watch?v=0Rq-yHAwYjQ&t=31692s) (Laracon speaker (employee), 3)
  - Why: pre-production validation and repeatable deployment support frequent releases.
  - Flag when: Release workflows bypass staging QA or require manual deployment after approved merges.
- **Consider** Allow delivery from main directly to production when passing automated tests and controlled feature rollout provide sufficient confidence to omit staging. — score 2: [James Mooring](https://www.youtube.com/watch?v=hpUrWWlBKCY) (Laracon speaker, 2)
  - Why: adequate automated safeguards can support a shorter release feedback loop.
  - Flag when: Direct production delivery lacks passing tests or controlled feature rollout.
- **Consider** Automate checks for required pull-request labels and workflow metadata. — score 2: [Sam Sehnert](https://www.youtube.com/watch?v=IPbxscS0xiY) (Laracon speaker, 2)
  - Why: early feedback exposes missing information needed to progress a review.
  - Flag when: Required review labels or metadata rely entirely on manual checks.
- **Consider** Automate container image builds and publication with scoped registry permissions, retention cleanup, and vulnerability scans. — score 2: [Justin Reasoner](https://www.youtube.com/watch?v=DdMFP_K0gv4) (Laracon speaker, 2)
  - Why: repeatable image delivery limits registry access and detects vulnerable artifacts.
  - Flag when: Image publication lacks scoped permissions, cleanup, or vulnerability scanning.
- **Consider** Choose a merge strategy that preserves useful history for bisecting regressions. — score 2: [Vanamerongen](https://x.com/vanamerongen/status/1805299748099997895) (Tier 2, 2)
  - Why: useful commit history helps locate regressions.
  - Flag when: Merge settings discard independently useful commits without an agreed history policy.
- **Consider** Keep the main branch stable once the application is live. — score 2: [Spatie](https://spatie.be/guidelines/version-control) (Tier 2, 2)
